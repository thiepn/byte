# Byte Audit — 2026-09-25

This audit was performed against `main` after Phase 28, starting from commit
`8acfd6451bc03be99ac31c0422f31e81b9a1cb30`.

The review covered:

- telemetry and diagnostic state
- Windows lifecycle/window interaction
- settings and native persistence boundaries
- local data recovery
- companion/Quick Panel async lifecycle
- accessibility and constrained-layout behavior
- Stable/Beta release selection
- hotfix/release workflow behavior

## Result

No confirmed critical remote-code-execution, arbitrary-shell, arbitrary-filesystem,
or data-exfiltration vulnerability was found.

The audit did find several correctness and resilience bugs that could leave Byte
showing stale state, persist a preference that Windows did not successfully
apply, lose recovery evidence after local-state corruption, or make maintenance
workflows choose the wrong release history.

## Confirmed bugs fixed

### 1. Critical diagnostic incidents bypassed reopen cooldown

**Severity:** Medium

`SustainedTracker` checked the reopen cooldown for High activation but not for
Critical activation. A recovered condition could therefore reopen immediately as
Critical even while its configured reopen suppression window was still active.

**Fix:** Both High and Critical activation now require the cooldown to have
completed. A regression test covers immediate critical re-entry.

### 2. Windows startup state could diverge from persisted settings

**Severity:** Medium

Changing **Start Byte with Windows** updated the HKCU Run value before writing the
new Byte configuration. If the config write then failed, Windows could contain the
new startup state while Byte persisted the old preference.

**Fix:** On persistence failure Byte now best-effort restores the previous startup
registration before returning the error.

### 3. Click-through state could disagree with the native window

**Severity:** Medium

`set_click_through` updated Rust/UI shell state before asking Tauri/Windows to
apply cursor-event ignoring.

**Fix:** Native state is applied first. Rust/UI state changes only after native
success.

### 4. Move Mode could partially disable click-through on failure

**Severity:** Medium

Entering Move Mode disables native click-through before showing/focusing the
companion. A later show/focus failure could leave native interaction changed while
the shell state still represented the previous mode.

**Fix:** Byte captures the previous interaction/visibility state and restores it
when Move Mode setup fails.

### 5. Repeated telemetry failures served stale health indefinitely

**Severity:** Medium

A telemetry source error merely delayed the next sample. Previously published
CPU/memory/status data could therefore remain visible indefinitely during a
persistent sensor/source failure.

**Fix:** Two consecutive source failures invalidate the snapshot, reset diagnostic
and telemetry source state, and publish the unavailable state to the companion.

### 6. Disabling monitoring left stale companion behavior

**Severity:** Medium

Turning System monitoring off invalidated the Rust cache, but the companion did
not receive that invalidation event. A prior BUSY/STRESSED/NEEDS_ATTENTION
animation could remain active indefinitely.

**Fix:** Disabling monitoring now publishes an unavailable snapshot to the
companion immediately.

### 7. Layout-changing preferences persisted even when native layout failed

**Severity:** Medium

Display-mode, size, edge-anchor, and full customization writes could persist before
the native resize/reposition operation. If Windows/Tauri then rejected the layout,
the UI reported failure while the failed preference remained on disk.

**Fix:** These operations capture the previous companion preferences and roll back
persistence plus the previous layout when the native application step fails.

### 8. Corrupt collection progress was silently overwritten

**Severity:** Medium

Malformed, oversized, invalid-UTF-8, or wrong-schema collection state was replaced
with defaults without preserving the original bytes.

**Fix:** Collection state is quarantined to `*.corrupt.json` before recovery.

### 9. Corrupt notification/activity state did not follow the config quarantine policy

**Severity:** Low/Medium

Config corruption preserved a quarantine file, but notification and Activity
state did not consistently do so.

**Fix:** A shared quarantine helper now covers config, collection, notification,
and Activity persistence.

### 10. Activity clear was not transactional

**Severity:** Low/Medium

The in-memory Activity timeline was cleared before the new empty file was
persisted. A disk error could make the UI report failure while the current session
had already lost its in-memory timeline.

**Fix:** Activity state is restored in memory if the clear persistence step fails.

### 11. Settings kept polling desktop awareness while unfocused

**Severity:** Low

Settings performed a permanent 1.5-second awareness poll for as long as the
surface was mounted, including while the main window was hidden/unfocused.

**Fix:** Polling starts on focus and stops on blur, with one passive refresh while
unfocused.

### 12. Quick Panel lacked robust dialog/focus/listener behavior

**Severity:** Low/Medium

The panel lacked dialog semantics, Escape handling, programmatic focus on open,
selected-state semantics, and rejection-safe asynchronous listener registration.

**Fix:** Added dialog/focus/Escape behavior, `aria-pressed`, alert semantics,
focus-aware refreshing, teardown-race-safe event subscriptions, and corrected
native-hide failure handling so a still-visible panel keeps refreshing and reports
partial Move/Tray success accurately.

### 13. Companion IPC/listener failures could become unhandled promise rejections

**Severity:** Low/Medium

Panel opening, Move Mode interactions, collection-discovery recording, initial
shell reads, and multiple Tauri event listener registrations lacked failure
containment.

**Fix:** Native interaction failures are caught and contained, event listener
registration is teardown-safe, and failed visual-preference application degrades
to the existing companion error surface.

### 14. Main navigation/accessibility semantics were incomplete

**Severity:** Low

The main application lacked skip navigation, current-page semantics, predictable
focus transfer after view changes, and selected-state semantics for several
segmented controls.

**Fix:** Added skip link, `aria-current`, main-content focus transfer,
`aria-pressed`, alert roles, and decorative-avatar hiding.

### 15. Apps diagnostics hid information at constrained widths

**Severity:** Low

The Apps table used hidden overflow and removed the Assessment column at narrower
desktop widths.

**Fix:** The table keeps all columns and becomes horizontally scrollable instead
of silently dropping diagnostic information.

### 16. Capture-exclusion status overstated Windows guarantees

**Severity:** Low

Settings said screen-capture exclusion was “active” based only on the preference,
although Windows may reject `WDA_EXCLUDEFROMCAPTURE`.

**Fix:** The UI now accurately says exclusion is **requested from Windows**.

### 17. Stable release history could be contaminated by Beta releases

**Severity:** Medium, release engineering

The tagged release workflow previously chose the most recently published release
without respecting Stable/Beta channel boundaries. A newer Beta could become the
comparison/upgrade source for a Stable release.

**Fix:** Stable builds select only previous non-prerelease releases. Beta builds
may consider prereleases.

### 18. Hotfix workflow was hard-wired to `main`

**Severity:** Medium, release engineering

This prevented a Stable patch-forward hotfix from a certified branch when
`main` was carrying future Beta work.

**Fix:** Hotfix dispatch now accepts an explicit certified `source_ref`, verifies
it descends from the base stable release, and requires an exact-commit successful
Packaging Certification run before tagging.

### 19. Unavailable telemetry gaps erased Activity transition continuity

**Severity:** Low/Medium

Activity replaced its previous valid diagnostic sample with an unavailable
snapshot. After telemetry recovered, Byte could no longer emit the eventual
Resolved event for an issue that had been active before the data gap.

**Fix:** Unavailable snapshots are treated as gaps rather than state transitions;
the last valid sample remains the comparison baseline.

### 20. Disabled Activity history leaked into later history decisions

**Severity:** Low/Medium, privacy/correctness

While Activity history was disabled, Byte still updated its in-memory transition
baseline. Re-enabling history could therefore create an orphan Resolved event for
an issue that occurred entirely while history was off.

**Fix:** Disabling history now clears the transition/trend baseline. The first
sample after re-enabling establishes a fresh baseline without recording disabled-
period transitions.

### 21. Byte allowed multiple concurrent app instances

**Severity:** Medium

Starting Byte twice could create duplicate trays/companions, duplicate low-level
input hooks, and concurrent processes writing the same local state files.

**Fix:** Byte now holds a Windows-exclusive instance lock file before Tauri starts.
A duplicate launch exits before initializing windows, hooks, telemetry, or local
stores. The OS releases the file handle automatically when the process exits or
crashes; a leftover file is harmless because the exclusivity is on the open
handle, not file existence.

### 22. Quick Panel stopped refreshing before native hide succeeded

**Severity:** Low/Medium

The panel stopped its refresh timer before asking the native window to hide. If
the hide call failed, the Quick Panel could remain visible while its system state
silently stopped updating.

**Fix:** The native hide is attempted first. Refreshing stops only after the
window was successfully hidden.

### 23. Quick Panel masked partial native success as total failure

**Severity:** Low

Tray mode and Move Mode could succeed, then panel closing could fail. The shared
`catch` path reported that the mode change itself failed even though Byte had
already entered the requested state.

**Fix:** Mode/Move changes and panel closing are handled as separate operations.
The panel now reports partial success accurately while retaining the successful
native state.

### 24. Monitoring toggles were not explicit diagnostic/history boundaries

**Severity:** Medium

Byte relied on the generic long-scheduler-gap reset to clear telemetry and
diagnostic state. A quick monitoring off/on cycle shorter than that threshold
could reuse the previous sustained-condition tracker and Activity comparison
baseline.

**Fix:** Monitoring enable/disable transitions now reset diagnostic tracking,
telemetry source state, sample-failure state, and Activity's observation
baseline. Disabling Activity history also clears its comparison baseline
immediately so later opt-in history cannot inherit disabled-period state.

### 25. Activity event writes could fail once and never retry

**Severity:** Medium

Issue/power transitions were appended to the in-memory Activity timeline before
the persistence write. `AppState` intentionally treats Activity persistence as
best-effort, so a failed write could leave the new event in memory, advance the
comparison baseline, and prevent a later sample from retrying that transition.
The event would then disappear on restart.

**Fix:** Event persistence is transactional. On a failed write Byte restores the
previous persisted event set, event ID, and comparison baseline so a later valid
sample can retry the transition.

## Additional audit conclusions

### Intentional behavior retained

- Collection typing progress is flushed in batches; a hard process/OS crash may
  lose the most recent unflushed typing increments. This is an explicit write
  amplification tradeoff, not treated as a data-integrity bug.
- Byte continues to preserve user app data on uninstall.
- Capture exclusion remains best-effort Windows behavior rather than a security
  guarantee.
- Update discovery remains user initiated; no background updater was introduced.
- Unsupported future config schemas continue to fail closed rather than being
  guessed/migrated.

### Release-track assumption

Byte still maintains one advancing Stable line plus optional future Beta work.
The audit enables Stable hotfix branches while main carries Beta development; it
does not introduce long-term support for multiple independent historical Stable
minor lines.
